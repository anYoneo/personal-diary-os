# Personal Diary OS

A private diary that remembers. Single-user by design, dark-first, markdown-native, with Discord as
the notification + quick-capture layer around it.

Built as a **modular monolith**: Next.js App Router for the web surface and the API, Prisma over
SQLite for storage, one background worker for reminders/reflections/delivery, and a Discord bot that
shares the exact same service layer as the web app.

```
┌──────────────────────┐        ┌───────────────────────┐
│  Next.js (web + API) │        │   Discord bot         │
│  app router, RSC     │        │   slash cmd + DMs     │
└──────────┬───────────┘        └───────────┬───────────┘
           │  service layer (src/lib/services)│
           └───────────────┬─────────────────┘
                           │
                  ┌────────▼────────┐      ┌──────────────────┐
                  │  Prisma / SQLite│◄────│ worker (scheduled)│
                  └─────────────────┘      │ reminders, daily  │
                                           │ weekly, on-this-  │
                                           │ day, outbox       │
                                           └──────────────────┘
```

Nothing in `src/discord/*` imports a page; nothing in `src/app/api/*` builds Discord payloads. Both
call `src/lib/services/*`, and outbound Discord messages go through an **outbox table** so a
notification that cannot be delivered is retried by the worker instead of vanishing.

## Quick start

```bash
npm install
node scripts/init-env.mjs      # creates .env with a generated SESSION_SECRET
npx prisma db push             # creates prisma/dev.db
npm run seed                   # creates your account
npm run dev                    # http://localhost:3111
```

`npm run seed` reads `SEED_EMAIL` / `SEED_PASSWORD` from `.env`. With neither set it generates a
strong random password and prints it **once** to the terminal.

### Commands

| Command | What it does |
| --- | --- |
| `npm run dev` | Web app on port 3111 |
| `npm run build` / `npm start` | Production build / serve |
| `npm test` | Vitest — unit + integration against a throwaway SQLite file |
| `npm run typecheck` | `tsc --noEmit` |
| `npm run lint` | ESLint |
| `npm run db:push` | Apply schema |
| `npm run db:studio` | Prisma Studio |
| `npm run bot` | Start the Discord bot (gateway, slash commands + DM capture) |
| `npm run worker` | Start the background worker (reminders, reflections, outbox delivery) |
| `npm run discord:register` | Register slash commands with Discord |

Run `bot` and `worker` as two long-lived processes next to the web app; the worker is what makes
reminders and reflections actually fire. On Windows, `scripts/run-services.cmd` starts all three.

## Configuration

Everything lives in `.env` (see `.env.example`; `.env` is git-ignored, and so is `prisma/dev.db`).

| Variable | Required | Notes |
| --- | --- | --- |
| `DATABASE_URL` | ✅ | `file:./dev.db` for SQLite |
| `SESSION_SECRET` | ✅ | generated by `init-env.mjs`; rotating it invalidates all sessions |
| `APP_URL` | ✅ | used in Discord links; default `http://localhost:3111` |
| `DIARY_TIMEZONE` | – | fallback timezone for new accounts, default `Asia/Jakarta` |
| `DISCORD_BOT_TOKEN` | – | enables the bot and all notifications |
| `DISCORD_APPLICATION_ID` | – | for slash-command registration |
| `DISCORD_NOTIFY_CHANNEL_ID` | – | where notifications are posted (a DM channel id works) |
| `DISCORD_GUILD_ID` | – | required for command registration; guild scope is the safe default |
| `DISCORD_CAPTURE_DMS` | – | `true` to turn DMs into entries; **leave unset if the token is shared** |
| `DISCORD_PUBLIC_KEY` | – | only to use HTTP-interaction mode instead of the gateway |
| `AI_BASE_URL` / `AI_API_KEY` / `AI_MODEL` | – | any OpenAI-compatible endpoint |

**The app is fully usable with zero Discord and zero AI configuration.** Where a feature needs them
it says so on screen — no button pretends to work. With Discord unconfigured, queued notifications
are marked `skipped` in the outbox and the settings page shows that state explicitly.

## Discord

1. Create an application + bot at <https://discord.com/developers/applications>.
2. Copy the bot token into `DISCORD_BOT_TOKEN` (plus `DISCORD_APPLICATION_ID` and `DISCORD_GUILD_ID`).
3. `npm run discord:register`, then invite the bot with the `bot` + `applications.commands` scopes.
4. Run `npm run bot`.
5. In the web app: **Settings → Discord → Generate link code**, then `/link <code>` in Discord.

Reusing an existing bot? `npm run discord:link` writes the token already present in your environment
into `.env` and resolves `DISCORD_APPLICATION_ID` + `DISCORD_NOTIFY_CHANNEL_ID` for you, so the token
never has to be pasted anywhere. `npm run discord:verify` proves the token is live and
`npm run discord:audit` lists existing commands before you register anything.

### Two guardrails you need to know about

Both exist because `DISCORD_BOT_TOKEN` may point at an application that **another gateway already
uses** (the Hermes agent gateway shares one, and it owns 75 global commands):

- **Command registration is guild-scoped and non-destructive by default.** Discord's command PUT is a
  full overwrite of the scope, so a global PUT would delete every other bot's commands. Registration
  refuses to run without `DISCORD_GUILD_ID`, fetches the existing list first, and merges unrelated
  commands back into the request. Global writes require an explicit `--allow-global`.
- **DM capture is off unless `DISCORD_CAPTURE_DMS=true`.** A second gateway on the same token receives
  the same DMs as the first, so with capture on, every DM you send your Hermes bot would also become
  a diary entry. Slash commands are unaffected — they cannot collide.

Linking is explicit and one-to-one: the bot refuses to capture anything from an unlinked Discord
account, so a shared channel can never write into your diary.

### Slash commands

| Command | Purpose |
| --- | --- |
| `/write` | Create an entry from Discord (optional type, mood, tags) |
| `/today` | Show today's entry |
| `/search <query>` | Full-text search |
| `/random` | Resurface a random old entry |
| `/remember <keyword>` | First/last mention and how often you've written about it |
| `/onthisday` | What you wrote on this date in earlier years |
| `/stats` | Writing stats for the current month |
| `/reflection` | Weekly/monthly reflection — facts first, interpretation labelled |
| `/goals`, `/threads`, `/thoughts` | Current goals, life threads, unresolved thoughts |
| `/remind <text> [when]` | Schedule a reminder |
| `/link <code>` | Connect your Discord account to the diary |

### Quick capture

Any DM to the bot becomes an entry. A leading prefix sets the entry type:

| Prefix | Becomes |
| --- | --- |
| `remember this: …` / `remember: …` | entry, content stored verbatim |
| `idea: …` | idea |
| `work: …`, `lesson: …`, `goal: …`, `random: …` | matching type |
| `question: …` / `unresolved: …` | reflection **+** an open unresolved thought |
| `mood: good …` | sets mood, marker stripped from the text |

`#tags` anywhere in the text become tags. A `---` front block is honoured for explicit `title`,
`type`, `mood` or `tags`. Stored metadata: source, channel id, message id, author id, and the
original timestamp.

## What's implemented

**Web** — Home/Today (greeting, streak, unresolved thoughts, on-this-day, recent themes), editor with
debounced autosave and a visible save state (`Saving/Saved/Offline/Syncing`), markdown preview, word
count, reading time, mood, type, tags, important flag; timeline with month/year navigation and
filters; search (full text + tag/type/mood/date range) with mention history; memories (on this day,
random, forgotten, first mention, last mention, ghost threads, life threads); goals; life threads;
unresolved thoughts; analytics; weekly/monthly reflection with facts separated from AI
interpretation; settings; trash with restore/purge; command palette (⌘/Ctrl-K); keyboard shortcuts
(`n`, `/`, `⌘↵`, `Esc`); light/dark themes.

**Data** — normalized schema with soft delete, audit trail, an outbox for outbound notifications,
entity/mention tables ready for an embedding column, and `ai_insights` in a separate table so
generated text can never be confused with your writing.

**Discord** — bot with 12 slash commands, DM quick capture, opt-in notifications, explicit linking.
Two modes: gateway process (`npm run bot`) or HTTP interactions when `DISCORD_PUBLIC_KEY` is set.

**Worker** — daily prompt, "on this day" (only when an entry actually exists on today's date in an
earlier year), weekly reflection (Fridays 17:00), pending reminder delivery, outbox delivery with
retry/backoff, quiet-hours hold, and cleanup of expired sessions and link codes.

**AI** — off by default; `POST /api/ai` summarises / tags / finds similar entries when a provider is
configured. Interpretation is always stored in `ai_insights` and rendered in a labelled block below
the original text. The endpoint reports `available: false` with a reason when nothing is configured.

## Data model, briefly

`User → Entry → { EntryTag → Tag, EntryThread → LifeThread, Attachment, Goal }` plus
`UnresolvedThought`, `Reminder`, `NotificationOutbox`, `AiInsight`, `DiscordLink`, `LinkCode`,
`Session`, `UserSettings` and `AuditLog`.

Decisions worth knowing:

- **`Entry.day`** is a stored `YYYY-MM-DD` string in the owner's timezone, indexed. Streaks,
  timelines, "on this day" and analytics query one indexed column instead of doing timezone
  arithmetic in SQL. Recomputed whenever an entry's timestamp or the user's timezone changes.
- **Soft delete** (`deletedAt`) with an explicit, audited purge. Only non-deleted rows count toward
  streaks, search and analytics.
- **No AI table shares a column with user writing.** Original text is immutable to the AI layer.
- **Entity tables exist but stay empty** until extraction is real: `Entity`/`EntryEntity` are ready,
  and the current life-thread view is computed from tags you actually used, so nothing is invented.

Full rationale: [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md).

## Privacy

Session-cookie auth, `scrypt` password hashing, rate limiting on login, registration and Discord
linking, no diary text in logs (errors log a code + id), no diary content in `localStorage`, and
`noindex` metadata.

**There is no open sign-up.** Registration is invite-only (`/register`), because an unrestricted
"create account" form would let any stranger who found the URL write into your server. The first
account (the operator) is seeded from `ADMIN_EMAIL` / `ADMIN_PASSWORD` at deploy time
(`scripts/seed.ts`). Every later account needs a single-use code minted by the operator:

```bash
npm run invite:new                          # one single-use code
npm run invite:new -- --note "istri" --days 7
npm run invite:list
npm run invite:revoke -- ABCD-EFGH
```

The same thing is available over HTTP from the operator's own session
(`GET`/`POST`/`DELETE /api/invites`), and only the operator's email — `BETA_ADMIN_EMAIL`, falling
back to `ADMIN_EMAIL` — is accepted.

### Each account is a separate diary

Every entry, tag, thread, goal, thought, reminder and setting is scoped by `userId`. Two accounts on
the same instance cannot see or touch each other's writing — this is enforced inside the queries
themselves (`where: { id, userId }`), not only by a check above them, so a route that forgets to
look cannot leak. Three things keep it that way:

```bash
npm run audit:scoping      # static scan: every query that touches user-owned data
npx vitest run             # tests/multiuser.test.ts — behaviour-level isolation tests
npm run verify:multiuser   # end-to-end: a second account over real HTTP vs the owner
```

To change the password later, edit `.env` and re-run `node scripts/deploy-migrate.mjs` after
deleting the user — or ask me to add a password-change screen in Settings.

The database is one file — back it up by copying it (`/root/diary-data/diary.db` on the VPS,
`prisma/dev.db` locally).

## Deploying

The app is three long-lived processes — web (`npm start`), `npm run worker`, `npm run bot`. Anything
that sleeps (free serverless tiers) breaks reminders and Discord, so deploy it where a process can
run continuously: a VPS, or a home machine behind a tunnel.

### Keep SQLite; do not reach for Postgres

SQLite is not a compromise here. This is a single-user diary: one writer, little concurrent load,
and one file is genuinely easier to back up than a database server. Postgres would also mean
generating migrations for a schema that has only ever used `db push`, plus a server to keep alive.

The one thing SQLite needs is for its file to live **outside the app directory**, on a volume:

| Where | `DATABASE_URL` |
| --- | --- |
| Docker | `file:/data/diary.db` (mount a volume at `/data`) |
| Bare metal / pm2 | `file:/home/ubuntu/diary-data/diary.db` |

Then upgrading, `git pull`, or rebuilding an image cannot delete the diary.

### Docker Compose (included)

```bash
cp .env.production.example .env.production     # fill it in
sudo bash scripts/oracle-bootstrap.sh          # Oracle host only: Docker + firewall + /data
docker compose run --rm web node scripts/deploy-migrate.mjs   # schema + owner account
docker compose up -d --build
npm run verify:deploy                          # proves login, write, read-back, delete
```

`docker-compose.yml` runs three containers from **one image** (only `web` builds; `worker` and `bot`
reuse it) sharing a `diary-data` volume. The web port is published on `127.0.0.1:3111` only — public
traffic must arrive through a tunnel.

### Bare metal (pm2, lighter)

```bash
npm ci && npx prisma generate && npm run build
node scripts/deploy-migrate.mjs                # or: npm run deploy:migrate
pm2 start scripts/ecosystem.config.cjs
pm2 save && pm2 startup                        # restart on reboot
```

### Exposing it

The container binds to loopback, so put a tunnel in front of it:

- **Cloudflare Tunnel** — needs a domain whose nameservers point at Cloudflare (a free `eu.org`
  subdomain works). Gives HTTPS, hides your IP, no open ports.
- **Tailscale Funnel** — needs no domain at all. `tailscale funnel 3111` returns a public
  `https://<host>.<tailnet>.ts.net` URL; put it in `APP_URL`.

`APP_URL` must be the public HTTPS URL, because Discord notifications link back into the app.

### Deployed: dalang.io VPS (`diary-vm`) — live

**URL:** https://diary.example.com
**Host:** Ubuntu 26.04 · 2 vCPU · 4 GB RAM · 20 GB SSD · no public IP · root via `dalang exec`
**Stack:** Node 24 (official tarball, not apt) + pm2 — **not Docker** (see why below)

```bash
# from this machine, one command, idempotent (~8 minutes: npm ci + Next build)
bash scripts/vps-update.sh
```

That script packages `HEAD`, uploads it, and runs the deploy detached (the `dalang exec` tmux
session cannot hold a multi-minute build, and a wrapped long command wedges it). Watch progress with
`dalang exec diary-vm "tail -c 600 /root/apply.log"`.

On the VM the pieces are: `scripts/vps-apply.sh` (extract + verify + run the deploy) and
`scripts/vps-launch.sh` (detached launcher). The real deploy is `scripts/dalang-deploy.sh`.

**Three traps this deployment hit, all now guarded in code — see the header comments:**

1. `NODE_ENV=production` exported *before* `npm ci` makes npm skip devDependencies, but the server
   needs `tailwindcss`/`@tailwindcss/postcss` to build and `tsx` to run the worker and bot. Install
   first.
2. A failed build must not fall through to `pm2 delete all` — that kills a healthy running app and
   leaves 502s. The script now requires `.next/BUILD_ID` before touching pm2.
3. Turbopack reuses `.next` verbatim, so a fixed config keeps producing the old error. The build
   clears the cache first, and `next.config.ts` pins `turbopack.root` to the project so the
   toolchain cannot wander up into a stray copy of the project (which is exactly what broke it once).

| Process | What it is |
|---|---|
| `diary-web` | `next start` on **0.0.0.0:80** |
| `diary-worker` | Discord notification outbox drainer |
| `diary-bot` | gateway bot, DM capture off |

`pm2 startup` is registered, so all three come back after a reboot.

#### Why port 80 and not a tunnel

dalang.io gives each VPS a free `*.svc.dalang.io` subdomain behind **Cloudflare**, and it forwards to
**port 80 on the VM**. `ipv4_public` is empty — there is no dedicated IP, so Tailscale/Funnel is
unnecessary. Verify from your laptop:

```bash
curl -I https://<id>.svc.dalang.io/login     # 200, TLS terminated by Cloudflare
```

Because the public scheme is HTTPS, **leave `COOKIE_SECURE` unset** — do not force it to `false`.

#### The tunnel goes cold — and that is what "slow" meant

The first click after a pause took ~7 seconds while the app itself answered in 16 ms. Measured on this
host:

| gap since previous request | time to first byte |
| --- | --- |
| 5 s | 0.14 s |
| 10 s | 6.85 s |
| 30 s | 6.83 s |
| never (curl `http://localhost/login`) | **0.016 s** |

So the Cloudflare → VM path is torn down after roughly **ten seconds of quiet** and costs ~7 s to
re-establish. dalang.io exposes no keep-alive or idle-timeout setting (`dalang --help`, `service info`),
and the VM itself never sleeps — loopback stays at 16 ms after 90 s idle.

The instance therefore keeps the path warm itself: **`scripts/keepalive.mjs`**, running as the pm2
process `diary-keepalive`, requests `/login` every **5 s**. `/login` is chosen deliberately — static
from the server's point of view, no session needed, and in the proxy's public allowlist.

```bash
dalang exec diary-vm "tail -5 /root/.pm2/logs/diary-keepalive-out.log"
```

It logs only on state changes (a cold beat or an unreachable tunnel), so a healthy log is nearly empty.
Result: the same idle-30 s request that took 7.7 s now takes ~0.9 s. Cost is a few hundred bytes per
five seconds. `scripts/vps-keepalive.sh` installs/refreshes it without a rebuild.

**A redeploy must not lose it.** `APP_URL` has to be in the environment pm2 captures, or the keep-alive
process exits immediately with nothing to warm; `dalang-deploy.sh` now reads it out of `.env`.

#### Why not Docker here

Ubuntu 26.04 is newer than the Docker and nodesource apt repos carry, so `apt-get install docker.io`
does not resolve. Node came from the official tarball instead (`scripts/vps-install-node.sh`). pm2 is
the lighter fit on a 20 GB disk anyway.

#### The SQLite trap that only shows up in production

Web, worker and bot all open the same SQLite file. With Prisma's default 5 s socket timeout the worker
failed every single tick:

```
Invalid `prisma.notificationOutbox.findMany()` invocation:
Socket timeout (the database failed to respond to a query within the configured timeout).
```

WAL alone was **not** the fix (Prisma already enables it). The fix is **one connection per process
plus a longer wait**:

```
DATABASE_URL="file:/root/diary-data/diary.db?connection_limit=1&socket_timeout=30"
```

`scripts/fix-db-concurrency.sh` applies it and restarts. Afterwards
`node ... src/worker/index.ts --once` prints `[worker] single pass complete`.

**Watch the endpoint format** — on Linux `ip route` shows `10.70.0.15` on `enp5s0`, but Cloudflare's
origin here is the **local/public endpoint** `172.17.0.1`, not the default route. So `WEB_HOST=0.0.0.0`
is required; do not bind to the local IP.

#### Operating it

```bash
dalang exec diary-vm "pm2 status"
dalang exec diary-vm "tail -20 /root/.pm2/logs/diary-worker-error.log"
dalang scp diary-vm:/root/diary-data/diary.db ./backup-$(date +%F).db   # backup
dalang exec diary-vm "bash /root/diary-app/scripts/dalang-deploy.sh"    # redeploy
```

**Keep `dalang exec` arguments short.** The persistent tmux session wraps long lines, and the injected
newlines get *executed* — which wedges the session inside an unterminated quote. Put anything long in a
`scp`'d script and run `bash /root/script.sh` instead.

#### dalang CLI notes

- Install: `curl -fsSL https://dalang.io/install.sh | bash`, or take the release binary directly.
- `dalang auth` is a device flow: it prints a code for **dalang.io/auth/cli**. That page requires you
  to be signed into the dashboard first, so log in there, then enter the code.
- `dalang exec` is genuinely flaky (502, "Failed to send command", "failed to fetch services",
  context deadlines). Wrap it in a retry loop; a single failure means nothing.

### dalang.io (no public IP, free subdomain → port 80)

> Satu perintah, langkah demi langkah: **[DEPLOY-DALANG.md](DEPLOY-DALANG.md)** (Bahasa Indonesia).

dalang.io gives every VPS a free `namamu.svc.dalang.io` subdomain, but **no dedicated public IP by
default** — the subdomain proxies to **port 80**. Two consequences:

```bash
# in .env.production
COOKIE_SECURE="false"        # plain HTTP: a `secure` cookie is silently dropped → login loops
APP_URL="http://namamu.svc.dalang.io"

# Compose substitutes ${VAR} from .env, NOT from .env.production:
WEB_BIND=0.0.0.0 WEB_PORT=80 docker compose up -d --build
```

Without `COOKIE_SECURE="false"`, login appears to succeed and then bounces straight back to
`/login` — the browser refuses to store a `secure` cookie over HTTP.

For SSH from your own machine (there is no public IP), install Tailscale on the VPS and locally:

```bash
curl -fsSL https://tailscale.com/install.sh | sh && sudo tailscale up
```

Then `ssh <user>@<tailscale-ip>`. Tailscale also opens a cleaner option: keep the container on
loopback and use `tailscale funnel 3111` for an HTTPS URL instead of the plain-HTTP subdomain — then
leave `COOKIE_SECURE` unset.

### Two traps already handled

- **The container binds loopback only.** Do not publish `3111` to the internet; the diary has no
  rate limiting beyond login and Discord linking.
- **Prisma's engine is pinned in `schema.prisma`** (`binaryTargets`). Detection depends on
  `openssl` being present at build time, and a slim Debian build image without it makes Prisma emit
  the openssl-1.1.x engine, which then fails at runtime on bookworm with *"could not locate the
  Query Engine"*. The Dockerfile installs `openssl` before `prisma generate` for the same reason.
